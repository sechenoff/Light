# Выдача и приёмка на складе: сессии киоска, завершение, аудит

**Зачем.** Аудит сентября 2026 нашёл в киоске склада ошибки, из-за которых сотрудники
обходили его кнопками на карточке брони:

- брошенная или устаревшая сессия блокировала «+ Добор» со страницы, а закрыть её было нечем
  (на проде 05.09 из-за этого завели новую бронь);
- «Готово» на забытом планшете возвращал принятую кнопкой бронь в «Выдана» и заводил
  потеряшки задним числом;
- повтор или параллельный «Готово» давал 500 «Сессия должна быть активной», двойные
  потеряшки, ремонты и записи пробега;
- выдача и приёмка в киоске не попадали в журнал брони: аудит писался после транзакции
  с именем кладовщика вместо пользователя, внешний ключ падал, ошибка проглатывалась;
- правка степпера пересобирала основную смету по текущему прайсу и вливала в неё
  доп-смету;
- киоск выдавал бронь за недели до начала без вопросов, а «Готово» с обнулёнными
  строками «выдавал» пустую бронь;
- «Сломан безвозвратно» по количеству уходил в «Ищем», ремонт по количеству терял
  позицию после правки состава задним числом;
- на штучном учёте «Готово» снимал все резервы, и приборы у клиента числились свободными.

**Какая сессия живая.** Правила — в `apps/api/src/services/scanSessionPolicy.ts`.

- Выдача (ISSUE) живая, только пока бронь подтверждена и не в архиве.
- Приёмка (RETURN) живая, только пока бронь выдана.
- Любая другая ACTIVE-сессия устаревшая. Она ничего не блокирует и не завершается.
  При первом обращении (`/state`, `/draft`, `/items`, `/complete`, `/cancel`, новое
  открытие брони) она закрывается с причиной `STALE`, в журнал брони пишется
  `SCAN_SESSION_CANCELLED`. Действие идемпотентное, поэтому `GET /state` может закрыть
  сессию.
- Ручные «Выдать», «Вернуть», отмена и архивация закрывают сессии брони в своей
  транзакции (карточка брони, `routes/bookings.ts`, `bookingLifecycle.ts`).
- Добор со страницы и правку состава блокирует только живая сессия, в которой уже есть
  работа: черновик, отметка или добор. Сессия «открыл и посмотрел» ничего не блокирует
  (`findBlockingScanSession`).

Восемь висящих сессий на проде стоят на уже принятых бронях. По этим правилам они
устаревшие и безвредны сразу после деплоя, базу руками не правим.

**Завершение (`completeSession`, `services/warehouseScan.ts`).** Сервис разбит на
части: `warehouseScanShared.ts` (типы и опции), `warehouseScanAdjustments.ts` (степпер
выдачи), `warehouseScanReconcile.ts` (экземпляры, ремонты, потеряшки),
`warehouseScanDetails.ts` (просмотр без изменений). Внешний API модуля прежний.

- До транзакции: закрытая сессия → 409, устаревшая закрывается и → 409 `SESSION_STALE`.
  Для выдачи раньше чем за сутки до начала → 409 `ISSUE_TOO_EARLY` с тем же текстом,
  что у кнопки; повтор с `force: true` проходит, в аудите `forcedEarlyIssue`.
- Первая запись транзакции — захват: `ACTIVE → COMPLETED` условным `updateMany` с
  `completedBy`. Из двух параллельных «Готово» проходит один, второй получает
  409 `SESSION_ALREADY_COMPLETED` с тем, кто и когда завершил.
- Устаревший экран: `itemsVersion` не совпал → 409 `CHECKLIST_OUTDATED`; `draftRevision`
  меньше серверной → 409 `DRAFT_OUTDATED` со свежим черновиком. Корректировка по строке,
  которой уже нет в брони, — тоже `CHECKLIST_OUTDATED`, а не 400. Оба поля
  необязательны: старый JS на планшетах их не шлёт.
- Степпер сверх заказа считается общей формулой склада (`stockCap.computeAddCaps`). Сверх
  свободного, но в пределах склада — 409 `ADDON_CONFLICT` с держателем и `bookingItemId`.
  С `acknowledgedConflict` проходит, пишется аудит `BOOKING_ITEM_ADDED_WITH_CONFLICT`.
  Сверх склада — 409 `ADDON_OVER_STOCK` с `bookingItemId`, киоск подсвечивает строку.
- Все строки обнулены → 409 `NOTHING_TO_ISSUE`, ничего не записано.
- Смена статуса брони, аудит `BOOKING_ISSUED` / `BOOKING_RETURNED`, изменения количества,
  ремонты и потеряшки по количеству, пробег машин — в одной транзакции
  (`timeout 20 с`). Штучные ремонты и потеряшки — после неё, каждая изолированно,
  как раньше.
- Автор аудита — сотрудник CRM, если киоск открыт его сессией. При входе по PIN
  автор `_system_` (`ensureSystemAuditUser` создаёт его отключённым, если строки нет),
  имя кладовщика — в `after.workerName`, открывший сессию — в `after.startedBy`.

**Смета при выдаче (`services/mainEstimate.ts`).** `applyIssuanceToMainEstimate`
заменил пересборку `recreateMainEstimate`. Строка MAIN уменьшается до выданного по цене
из снимка. Строка, по которой ничего не выдано, удаляется. Прибавка сверх сметы
остаётся доп-сметой. Исключение — произвольная позиция: доп-смета её не видит (нет
`equipmentId`), поэтому прибавку по ней держит сама основная смета по цене из снимка,
иначе довезённое ушло бы бесплатно. Итоги считаются через `splitEquipmentDiscount`:
скидка не ложится на договорные строки. Estimate.id сохраняется.

**Приёмка по количеству.** Ремонт и потеряшка пишут прямую ссылку на позицию
(`equipmentId`). «Сломан безвозвратно» сразу закрыт списанием: `WROTE_OFF`, поля
закрытия из `problemItemService.writeOffFields`. Такая карточка по-прежнему
вычитается из склада, как и раньше вычиталась «ищем».

**Штучный учёт.** На выдаче позиция без отметок по экземплярам выдаётся по живым
резервам, как кнопкой: свободные переходят в ISSUED. Позиция с отметками выдаётся
по отметкам, как раньше. Степпер сверх заказа резервирует свободные экземпляры. На
приёмке на полку переводятся только выданные и числящиеся пропавшими экземпляры:
прибор в открытом ремонте остаётся MAINTENANCE.

**Маршруты киоска (`routes/warehouse.ts`).**

- `POST /sessions`: живая сессия продолжается (`resumed`). Устаревшие сессии брони
  закрываются, их id приходят в `closedStaleSessionIds`. Тело черновика в ответ не
  отдаётся, только `hasDraft`, сам черновик — в `/state`. Выдача уже выданной
  брони — 409 `BOOKING_WRONG_STATUS` с подсказкой про «+ Добор»; архивной — 409
  `BOOKING_ARCHIVED`.
- `POST /sessions/:id/complete`: плюс `force`, `itemsVersion`, `draftRevision`,
  `issuanceAdjustments[].acknowledgedConflict`. В ответе плюс `bookingStatus`,
  `completedBy`, `manualFinalAmount`, `addonsAddedInSession`.
- `PUT /sessions/:id/draft { revision, draft }` → `{ revision, savedAt }`. Сам
  черновик — `services/checklistDraft.ts`.
- `POST /sessions/:id/cancel { reason?, onlyIfEmpty? }` → сессия и `cancelled`.
  Разрешённые причины: `KIOSK_ABORT`, `CARD_ABORT`, `EMPTY_LEAVE`. С `onlyIfEmpty`
  сессия с работой не трогается (`cancelled: false`). Завершённая или прерванная
  сессия — 409, а не 500.
- `GET /sessions/:id/addon-search` проверяет окно «с текущего момента до конца брони»
  (`issuingNow`).
- `GET /in-work/:id/details` не показывает строки, обнулённые на выдаче.

**Журнал склада и «Как пропало».** Выдал или принял тот, кто нажал «Готово»:
`completedBy ?? workerName`. Этим полем пользуются журнал рабочего стола (в том числе
фильтр «мои»), «Моя выработка» и `equipmentTrail`. Пробег машин записывается от имени
завершившего.

**Решения владельца (что сделано сейчас, остальное — во втором PR).**

- Договорной итог: добор его не меняет, киоск показывает предупреждение и
  договорную сумму.
- Хвост занятости просроченной выданной брони — «до текущего момента».
- Стык-в-стык не пересекается.
- «Под ответственность» при держателе ISSUED разрешено, но названо «у клиента с …».
- Пробег при ручном «Вернуть» пока только предупреждение.

**Подводные камни.**

- Откатить PR через Revert нельзя: `schema-guard` увидит удаление полей
  `ScanSession.draft*`, `completedBy`, `cancel*`. Чинить вперёд.
- Аудит теперь внутри транзакции выдачи. Если внешний ключ не пройдёт, откатится
  вся выдача, поэтому автор — всегда существующий пользователь или `_system_` через
  `ensureSystemAuditUser`.
- `itemsVersion` считается по ВСЕМ позициям брони, включая строки ×0, одной функцией
  `computeItemsVersion` на сервере и в `/state`.
