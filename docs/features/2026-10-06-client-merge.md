# Объединение клиентов-дублей и смена клиента у существующих броней

**Зачем.** Один и тот же клиент жил в справочнике несколько раз: «Петя Куб»,
«петя куб», «Петя  Куб». Брони, долг и счета расползались по карточкам, долг в
реестре делился на части. Причина — SQLite сравнивает кириллицу с учётом регистра:
поиск `contains` не находил «Петя Куб» по «петя», окно выбора клиента предлагало
«создать нового», а бронь заводила клиента по точному имени.

## Что сделано

- **Поиск без учёта регистра и «ё/е»** — `GET /api/clients?search=` фильтрует в
  приложении (`searchClientIds`, `services/clientNames.ts`): сначала имена, которые
  начинаются с введённого, потом остальные. Им пользуются окно смены клиента,
  автодополнение формы брони, справочник, фильтры финансов.
- **Одно правило «это то же имя»** — `normalizeClientName`: без регистра, «ё» = «е»,
  без кавычек, пробелы схлопнуты. Зеркало на вебе — `src/lib/clientName.ts`, менять
  оба вместе.
- **Новых дублей не появляется.** `POST /api/clients` и переименование —
  409 `CLIENT_NAME_TAKEN`, в `details` — `{ clientId, name }` существующего. Окно
  смены клиента в ответ на «создать нового» выбирает существующего. Бронь
  (`/draft`, `/quick`, превью) и счёт на оплату прикрепляются к существующему клиенту
  в любом написании (`findClientByName` / `resolveClientForBooking`). Если дублей
  уже несколько, берётся карточка с бо́льшим числом броней.
- **Объединение карточек** (только руководитель) — кнопка у строки в
  «Администрирование → Клиенты». Шаг 1: «Похожие имена» (`GET /:id/similar`,
  сходство Дайса по парам букв + порядок слов не важен, порог 0.6) и поиск. Шаг 2:
  какое имя оставить (по умолчанию карточка с бо́льшим числом броней) и сводка
  `GET /:id/merge-preview?into=` — сколько броней, счетов на оплату, кредит-нот и задач
  переедет, что станет с контактами и кабинетом. `POST /:id/merge { intoClientId }`
  делает то же одной транзакцией (`services/clientMerge.ts`).
- **Смена клиента у брони с продолжениями** — сразу у всей семьи (основная и
  продолжения), с любой брони семьи (`moveBookingFamilyToClient`,
  `services/bookingClient.ts`). Раньше — 409 `HAS_CONTINUATION`, и ошибочного клиента
  было не исправить. Финансовые исправления (`PATCH /:id/finance-corrections`) тоже
  меняют клиента у всей семьи. Окно смены предупреждает об этом.
- **Длинный проект** — «Сменить» у клиента в шапке проекта. Это операция проекта
  `POST /api/booking-projects/:id/client { revision, clientId }`: со сверкой ревизии и
  записью в «Историю проекта». Обычный путь `/api/bookings/:id/*` для проектов закрыт
  (409 `PROJECT_ACTION_REQUIRED`). Менять можно и у завершённого проекта — правка
  «бумажная».

## Что делает объединение

Дубль вливается в основную карточку, дубль удаляется. Имя остаётся у основной.

| Что | Как |
|-----|-----|
| Брони (все, включая архив) | переходят к основной; у каждой — запись «Клиент брони изменён», причина «Объединение карточек клиента» |
| Счета на оплату | переходят; выписанный документ не меняется — плательщик в снимке прежний |
| Кредит-ноты, задачи | переходят |
| Телефон, почта | пустые у основной — дозаполняются; разные — у основной свои, чужие дописываются в комментарий строкой «Из «дубль»: тел. …; почта …» |
| Комментарий | пустой у основной — переносится; иначе дописывается той же строкой |
| Реквизиты для счёта | переносятся **набором** и только если у основной их нет совсем; иначе остаются свои, ИНН дубля — в комментарий (смешивать наборы нельзя) |
| Доступ в кабинет | только у дубля — переезжает; у обоих — остаётся кабинет основной, кабинет дубля закрывается (видно в сводке до подтверждения) |
| Журнал | `CLIENT_MERGE` у основной (что перенесено), `CLIENT_MERGED_INTO` у дубля |

## Подводные камни

- **Кабинет клиента берёт клиента из учётной записи, а не из токена** (`lkAuth`).
  Иначе сессия, выданная до объединения, смотрела бы в удалённую карточку дубля.
- **Предпросмотр и объединение считают план одной функцией** (`planClientMerge`) —
  окно показывает ровно то, что произойдёт.
- **Журнал: ссылка рядом с именем не показывается** (`auditFormat.flatten`): если в
  записи есть `clientName`, строка `clientId` не дублирует её. Иначе удалённая карточка
  читалась бы как «Запись № …».
- 409 `CLIENT_NAME_TAKEN` теперь в 4-аргументной форме `HttpError`: код — в
  `res.body.code`, в `details` — существующий клиент (раньше в `details` лежала строка
  кода).
- Отменить объединение нельзя: дубль удаляется. Окно пишет это до подтверждения.
