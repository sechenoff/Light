# Анонимный доступ к каталогу: гард маршрутов + deny-by-default в прокси

Дата: 2026-09-16
Статус: утверждено к реализации

## Проблема

`apps/api/src/routes/equipment.ts` монтируется голым (`router.use("/api/equipment", equipmentRouter)`),
а три его read-маршрута (`GET /`, `GET /categories`, `GET /:id`) не имеют `rolesGuard`.

Само по себе это дало бы «каталог видит любая аутентифицированная сессия». Но в связке с
Next-прокси (`apps/web/app/api/[...path]/route.ts`), который подставляет `X-API-Key`
**каждому** запросу, включая анонимный, это означает: `svetobazarent.ru/api/equipment`
отдаёт прайс-лист и состав парка кому угодно без входа в систему.

Это тот же класс проблемы, что описан в «Закалке доступа (2026-09-01)»: ключ в прокси
работает не как гард, а как **анти-гард**. Любой маршрут без `rolesGuard` автоматически
становится публичным.

## Аудит: что доступно анонимно сегодня

Метод — не чтение кода, а прогон: приложение поднято с `AUTH_MODE=enforce`, обойдена вся
таблица маршрутов Express, каждый маршрут вызван ровно так, как это делает прокси для
анонимного посетителя — только `X-API-Key`, без сессии.

**265 маршрутов, 255 отвечают 401.** Анонимно доступны десять:

| Маршрут | Ответ | Оценка |
|---|---|---|
| `GET /health` | 200 | штатно |
| `POST /api/auth/login` | 400 | штатно — форма входа |
| `POST /api/auth/logout` | 200 | штатно — гасит cookie |
| `POST /api/lk/auth/request-login` | 400 | штатно — magic-link, без энумерации, rate-limit |
| `POST /api/warehouse/auth` | 400 | штатно — PIN киоска, свой lockout |
| `GET /api/warehouse/workers/names` | 200 | штатно — экран входа киоска |
| `GET /api/equipment` | 200 | **дыра**: названия, категории, остатки, три тарифа |
| `GET /api/equipment/categories` | 200 | **дыра**: карта склада со счётчиками |
| `GET /api/equipment/:id` | 200 | **дыра**: карточка позиции |
| `POST /api/users/upsert` | 400 (валидация) | **дыра на запись**: анонимный upsert в `User` |

Остальной периметр закрыт корректно: `/api/equipment/:id/units/*`, `/api/equipment-units/*`,
весь `/api/lk/*`, все сканер-маршруты склада → 401 без сессии.

Побочная находка: `POST /api/users/upsert` — анонимная **запись**. Гарда нет вообще,
единственный потребитель — `apps/bot/src/services/api.ts`.

## Что не должно сломаться (проверено)

- **Киоск склада каталог не читает.** Quick-add ходит в `/api/warehouse/sessions/:id/addon-search`,
  а не в `/api/equipment` — гард каталога киоска не касается.
- **Бот:** `GET /api/equipment(/:id)?` уже в `BOT_WHITELIST` (паттерн `(\/[^/]+)?` покрывает
  и `/categories`), `rolesGuard` пропускает по `req.botAccess`. Каталог боту остаётся.
- **Портал `/lk`** каталог не трогает — работает через Prisma в своих роутах.
- **Публичной витрины нет.** Анонимные страницы: `/login`, `/lk/login`, `/lk/login/sent`,
  `/lk/verify`. Их API-вызовы — только `/api/auth/*`, `/api/lk/auth/*` и два публичных
  складских.
- **`COLLECTOR` в репозитории отсутствует** — в `UserRole` три значения. Закрываем для них.

## Решение

### 1. Гард на каталог (сервер)

В `routes/index.ts` монтировать с `rolesGuard(["SUPER_ADMIN", "WAREHOUSE", "TECHNICIAN"])` —
ровно то, что обещает матрица прав в CLAUDE.md (`GET /api/equipment` = ✓ для всех трёх ролей).
Per-route гарды на `POST`/`PATCH`/`DELETE` внутри роутера остаются и сужают дальше.

Гард ставится на **монтировании**, а не на трёх хендлерах: иначе четвёртый read-маршрут,
добавленный завтра, снова окажется голым. Единица защиты — префикс.

### 2. Гард на `users/upsert` + строка в bot-whitelist

`rolesGuard(["SUPER_ADMIN", "WAREHOUSE"])` на `/api/users` + `POST /api/users/upsert` в
`BOT_WHITELIST`. Ручку и модель `User` не удаляем: решение о судьбе бота (Known Issue №8) —
отдельное, а держать дыру открытой до него нельзя.

### 3. Прокси: deny-by-default

`apps/web/app/api/[...path]/route.ts` перестаёт подписывать `X-API-Key` анонимному запросу.

Публичный allowlist (единственное, что проходит без учётных данных):

- `/api/auth/*` — вход, выход, `/me` (вызывается до входа, чтобы понять, есть ли сессия);
- `/api/lk/*` — у портала своя цепочка `lkAuth`, все его непубличные маршруты уже 401;
- `POST /api/warehouse/auth` — вход киоска по PIN;
- `GET /api/warehouse/workers/names` — список имён на экране входа киоска.

Всё остальное требует хотя бы одного признака сессии на входящем запросе:
cookie `lr_session`, cookie `lk_session` или заголовок `Authorization`.
Нет ни одного → 401 `{ code: "UNAUTHENTICATED" }` **из прокси**, не доходя до сети.

Прокси проверяет **наличие** учётных данных, а не их валидность. Он не орган авторизации —
он лишь перестаёт выдавать анонимному посетителю ключ доступа. Решает по-прежнему API.

Почему 401 из прокси, а не «просто не подставлять ключ»: без ключа ответ зависит от
`AUTH_MODE`, и в режиме `warn` запрос прошёл бы дальше. Явный 401 детерминирован.

### 4. Сторож вместо трёх ассертов

Тест, который обходит таблицу маршрутов Express и требует: **каждый маршрут отвечает 401
без сессии, кроме явного allowlist**. Ловит следующий незакрытый роут, а не только эти четыре.

Allowlist в тесте — та же шестёрка, что в разделе «Аудит». Добавление роута в него —
осознанное действие, видимое в diff и на ревью.

## Риски

- **Прокси-гард — самое рискованное изменение**: ошибка в allowlist ломает вход.
  Митигация: allowlist выведен из кода (`components/warehouse/api.ts` явно документирует
  два публичных складских маршрута; `lib/auth.ts` — только `/api/auth/*`), и покрыт
  unit-тестами на обе стороны решения.
- **Ссылки `<a href>` из киоска на `/api/addon-estimates/:id/export/pdf`** не несут
  Bearer-заголовка. Они уже сегодня отвечают 401 при PIN-входе без главной сессии
  (подтверждено прогоном) — прокси-гард меняет источник 401, но не поведение.
  Для SA/WH с главной сессией cookie есть, ссылка работает как прежде.

## Вне рамок

- Удаление ручки `users/upsert` и модели `User` — вместе с решением о судьбе бота.
- Роль `COLLECTOR` — её в этом репозитории нет.
- Ротация `API_KEYS` — ключ не утекал, он работал по назначению; проблема в том, что
  прокси выдавал его анониму.
